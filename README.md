# AI-Based Soybean Sowing Window Predictor — Ahilyanagar, Maharashtra

A college AI/ML mini-project. For a **candidate soybean sowing date** it classifies the date as **safe** or **not safe**
according to a **rainfall-based rule**, using only weather and climate-index information that exists *before* that date.
It includes a reproducible data pipeline, a leakage-aware model evaluation, a Flask API and a small web dashboard.

> **What this project is not.** It does **not** predict yield, does **not** guarantee crop success, and does **not**
> establish the *optimal* sowing date. The target is generated by a rule from rainfall (below); it is not a verified sowing
> outcome. Yield-based sowing-window optimisation is a future extension that needs observed yield and sowing-date data.
> There is **no live weather / forecast integration**; the web app replays archived data or uses values you type in.

---------------------------------------------------------------------------------------------------

## 1. Objective and the key honest result

Given the weather of the days before a candidate date (rain, temperature, soil water, humidity, evapotranspiration) and
lagged climate indices (ENSO, IOD, SOI), predict whether the date is `safe` (1) or `not safe` (0).

**What the evaluation shows** (full detail: `reports/model_evaluation.txt`):

| | Validation 2007-2018 (rolling origin) | Held-out test 2019-2025 |
|---|---|---|
| Majority-class dummy | — | accuracy 0.49, recall 0 |
| **Rain rule** (rain since 1 May ≥ 75 mm; past-only) | F1 **0.842**, balanced acc. 0.921 | F1 1.000, balanced acc. 1.000 |
| **Random Forest** (selected on validation) | F1 0.778, balanced acc. 0.859 | F1 1.000, balanced acc. 1.000 |
| Decision Tree / Logistic Regression | F1 0.767 / 0.734 | F1 0.933 / 0.955 |

Read this carefully:

* The **test years are "easy"**: in 2019-2025 the label equals the simple rain rule on **100 %** of rows (zero
  "false starts"), so both the rule and the model score 1.000. This does **not** show extra skill; it shows that those years were wet.
* On the validation folds and in an exploratory leave-years-out check over all 31 years, the model is **no better than the
  one-line rain rule** (F1 0.837 vs 0.839) and catches only **1 of 35 "false starts"** (dates that had enough rain so far but a dry spell followed).
* Feature ablation (validation only): dropping the four climate indices does not hurt (F1 0.783 vs 0.778), and just `rain_cum_may1` + `doy` scores F1 0.811, higher than all 15 features. The ENSO/IOD/SOI features show no demonstrated benefit.
* Why: condition 1 of the label is *exactly* the feature `rain_cum_may1`, and conditions 2-3 depend on rain **after** the date,
  which past weather barely predicts. The model essentially re-learns "has it rained ≥ 75 mm since 1 May?".
* Therefore the project does **not** claim Random Forest is the best model, nor that ML beats the rule.

## 3. Data sources

| Data | Source | File |
|---|---|---|
| Daily rain, Tmax, Tmin, ET0 | Open-Meteo Historical Weather API (ERA5 reanalysis), grid point 19.09 N, 74.74 E | `data/raw/weather_daily.csv` |
| Hourly soil moisture 0-7 cm, relative humidity 2 m → daily means (only for days with all 24 hours) | same API (ERA5-Land soil moisture; ERA5 humidity) | same file |
| ONI (ENSO) | NOAA PSL `oni.data` | `data/raw/oni_raw.txt` → `oni.csv` |
| DMI (Indian Ocean Dipole) | NOAA PSL `dmi.had.long.data` (HadISST) | `dmi_raw.txt` → `dmi.csv` |
| SOI | NOAA PSL `soi.data` | `soi_raw.txt` → `soi.csv` |

Coverage: 1 Apr - 31 Aug of **1995-2025** (31 seasons × 153 days; no missing values), 9 candidate dates per year
(18 May … 13 Jul, weekly) = **279 rows**. Weather is reanalysis at one grid point, not gauge data.

**Download procedure** (needs internet; everything else works offline from the cache):
`python src/1_download_weather.py` downloads only years missing from the cache (`--force` re-downloads), retries on network/HTTP
errors, validates the result, writes atomically and keeps the previous file as `weather_daily.csv.bak`.
`python src/2_prepare_indices.py` refreshes the indices, falling back to the cached raw files; a bad download never replaces a good cache.

## 4. Features (details in `docs/feature_dictionary.md`)

All 15 inputs use only data **before** the candidate date.

| Feature | Meaning | Unit |
|---|---|---|
| `doy` | day of year of the candidate date | day |
| `rain_7d`, `rain_14d` | rain in the previous 7 / 14 days | mm |
| `rain_cum_may1` | rain from 1 May to the day before the date | mm |
| `rain_days_14d` | days with ≥ 2.5 mm in the previous 14 days | days |
| `days_since_rain` | days since the last ≥ 2.5 mm day (60 = none since 1 Apr) | days |
| `tmax_7d`, `tmin_7d` | mean daily max / min temperature, previous 7 days | °C |
| `soil_7d` | **modelled topsoil water content** (ERA5-Land, 0-7 cm), mean of previous 7 days | m³/m³ |
| `rh_7d` | **atmospheric (air) relative humidity** at 2 m, mean of previous 7 days — *not* soil moisture | % |
| `et0_7d` | FAO-56 reference evapotranspiration, mean of previous 7 days | mm/day |
| `oni`, `oni_change` | ENSO index (season centred 2 months earlier) and its 3-month change | °C |
| `dmi`, `soi` | IOD index and SOI of the previous month | °C / index |

Climate-index caveat: for candidate dates in the first days of a month, the nominal "previous month" value may be published
by NOAA a few days *after* that date. The validation ablation in `reports/model_evaluation.txt` shows the effect of removing the indices.
Neither `year`, `decision_date`, `safe_label`, `year_class` nor `year_class_3` (derived from labels) is ever a model input.

### Missing-data policy
Nothing is invented. Rainfall is never filled. Continuous variables may be carried forward from the *previous* days for at most 3 days
(never from the future, never across years). A feature whose window still has a gap is blank, and the row is **excluded and listed** in
`reports/data_quality.json`. Missing rain in a label window gives an unknown label, not "0 mm". Impossible values (e.g. humidity > 100 %) and
conflicting duplicate dates stop the pipeline with a clear error. The current cache is complete, so no row is excluded.

## 5. How the labels are built

`safe_label = 1` only if **all** hold (thresholds kept exactly as in the original project):

1. **Rain from 1 May to the day before ≥ 75 mm** — stands in for "the soil has been wetted". (The original project notes attribute 75 mm to MPKV Rahuri / KVK advice; this was *not* re-verified offline.)
2. **Rain in the 21 days starting on the date ≥ 40 mm** — stands in for enough water for germination / establishment (project assumption).
3. **No dry spell ≥ 10 consecutive days** in those 21 days — a dry day is < 2.5 mm (the usual IMD "rainy day" convention); project assumption.

Conditions 2 and 3 use rain **after** the date: they are retrospective and are never model inputs. All thresholds are assumptions needing
agronomic validation. There is no upper rain limit (waterlogging is ignored).
Class balance: **91 safe / 188 not safe (32.6 %)**; 3 of 31 years have no safe date. `reports/label_summary.txt` gives counts per year and date;
`python src/7_label_sensitivity.py` re-labels with 27 alternative thresholds (safe share 25-41 %; thresholds are *not* chosen by model performance).

## 6. Set-up

```bash
python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
```
Tested with Python 3.12 (pandas 3.0, scikit-learn 1.8, Flask 3). Model files are pickles: if scikit-learn warns about a version mismatch or
refuses to load the model, simply re-run `python src/6_train_model.py` (deterministic, about 1.5 minutes).

## 7. Run the data pipeline

```bash
python src/run_pipeline.py                  # offline: steps 2-7 from the cached raw data
python src/run_pipeline.py --download       # first refresh raw data (internet), then everything
python src/run_pipeline.py --skip-train     # data preparation only
```
or step by step: `python src/2_prepare_indices.py --offline`, `3_build_features.py`, `4_make_labels.py`, `5_merge_final.py`.
Re-running is safe: processed files are rebuilt from scratch (no duplicates); raw data is never modified by steps 3-7; the pipeline
reproduces the originally committed processed CSVs byte-for-byte (checked by a test).

## 8. Train and evaluate

```bash
python src/6_train_model.py                 # add --fast for a quick check, --test-start-year 2021 to change the split
```
Protocol: all splits are by **whole years**. Test = 2019-2025 (never used for fitting, feature choice or tuning). Development = 1995-2018 with
rolling-origin validation (train 1995-2006 → validate 2007-09; … → validate 2016-18). Random Forest, Decision Tree and scaled Logistic
Regression are tuned on development years only (selection: pooled validation F1 of the "safe" class). Baselines: majority Dummy and the past-only
rain rule (the full rule needs future rain, so it would be an oracle, not a fair baseline). Metrics: accuracy, precision, recall, F1, balanced
accuracy, confusion matrix, false-safe counts, Brier score, ROC-AUC, 95 % year-bootstrap intervals; plus false-safe analysis, feature-group ablation
and an exploratory leave-years-out check. The saved model is fitted on 1995-2018 only. Outputs: `models/best_model.joblib`, `models/features.json`,
`models/metadata.json`, `reports/model_evaluation.json|txt`. If the data cannot support an honest evaluation (e.g. one class only) training stops and writes nothing.
The "best model" is the best *learned* model on validation; the report states whether it beats the rain rule.

## 12. Limitations and future work

* The target is a rule on rainfall, with thresholds that need validation by an agronomist; it is not yield or verified sowing success.
* The model adds no demonstrated value over the one-line rain rule; the future-rain part of the label is not predictable from these features.
  Skill would have to come from forecast data (e.g. IMD / NWP rainfall forecasts) — **not implemented**, and never faked.
* Test years 2019-2025 contain no false-start rows, so they cannot test the hard cases; only 31 seasons exist and rows within a year are correlated.
* Probabilities are uncalibrated; the decision threshold is the default 0.5 (no cost-sensitive tuning).
* ERA5 reanalysis at a single grid point; soil moisture is modelled; climate-index publication lag (section 4).
* Future work: live data + forecast integration (using only information available at prediction time), observed yield / sowing-date data to
  optimise the sowing window, calibration, district-level multi-location data, expert-validated thresholds.

## 13. Sowing Prediction Demo (simulated, frontend-only)

`http://127.0.0.1:5000/demo` (linked from the dashboard) is a presentation-only preview of what a finished sowing-recommendation product
could look like. It is clearly labelled **"Demo Prediction — Simulated Data"**.

* **Simulated:** everything on `/demo`. A small transparent scoring rule (`static/js/demo_sim.js`) runs in the browser on the values typed
  into the form: an illustrative sowing window, a 0-100 *demo score*, risk by date, the "Why this demo result?" factors and next steps.
  Same inputs always give the same output (no `Math.random`, no clock). Dates after the assessment date use a fixed, repeating wet/dry
  rainfall pattern; it is **not** a weather forecast. The demo score is **not** a model probability or confidence, and the factor bars are
  **not** Random Forest feature importances.
* **Not touched:** the trained model, features, labels, thresholds, inference code, reports and every existing route/API. The `/demo` route only renders a template; the page
  makes no `fetch` calls, needs no internet and no API key. The inputs use the same names and ranges as `models/features.json`
  (9 of the 15 features; the rest are not needed for the illustration).
* **Real:** the *Predict* and *Method & results* tabs on `/` still use the trained Random Forest and the archived ERA5 data.
* Files: `templates/demo.html`, `static/js/demo_sim.js`, `static/js/demo.js`, `static/css/demo.css`, `tests/test_demo.py`
  (plus a link in `templates/index.html`, a `/demo` route in `app.py` and a few CSS lines in `static/css/style.css`).
